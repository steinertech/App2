# App.Server/plane — planes, grids, Design and Content

Plane-specific logic lives in `App.Server/plane/` — one file per plane served to App.Web (`plane-project.ts` with the project and user grids, `plane-debug.ts` with the Debug page's single `DebugDto` grid ("Debug Data"), `plane-debug-dynamic.ts` with the Debug Dynamic page's (plane `debugDynamic`, `page/DebugDynamic.tsx`) single `DebugDynamicSchemaDto` grid ("Debug Dynamic Schema", built like the Debug Data grid by `gridDataLoad`), `plane-debug-property.ts` with the Debug Property page's (plane `debugProperty`) master `DebugContentDto` grid ("Debug Content", built like the `DebugDto` grid by `gridDataLoad`) and its detail `DebugPropertyDto` grid ("Debug Property"; New, edit and Save only: no Column Chooser or Delete) and a third grid "Debug Table" (`grids[2]`, `gridDebugTableLoad`, rebuilt on plane load, Select and the Debug Property grid's Reload): if the `ownerType` `Row` properties of the selected row have a whole-number `RowCount` and `ColumnCount` (each clamped to 0..50), that many rows of read-only "Empty" label cells under header columns named by `indexToColumnNameExcel`, otherwise empty; it sets `isSelectPatch`/`isSelectColumnPatch`, and while one of its cells is selected the Debug Property grid shows that cell's properties instead (`gridDebugPropertyOwners`: owner `{ ownerName: 'RowIndex/<rowIndex>/ColumnName/<columnName>/', ownerType: 'CellTable' }`, also used by plane load, Reload and Filter Multi; a Debug Content Select rebuilds the table without selection), `plane-storage.ts` including the Image Preview grid, `plane-schema.ts`, `plane-dynamic.ts`, `plane-design.ts`, `plane-content-view.ts` with the `contentView` plane of the `Content.tsx` component (one grid per Table/Form band), plus `plane-design-master-detail.ts` with the Design plane's Design Master Detail grid, used by `plane-design.ts`). Each plane has one loader `(request, gridPlaneDto) => Promise<GridPlaneDto>` registered in `PLANE_LOADERS` in `util/api/util-grid-plane.ts` (it also builds any grid depending on another grid of the plane, e.g. the Image Preview of the selected storage row), and optionally one patcher of the same signature in `PLANE_GRID_PATCHERS` (returns `GridDto.patches` per grid, `grids[i]` for the incoming `grids[i]`; a `GridPatchEnum.Grid` patch replaces or removes that whole grid, e.g. the Image Preview after `GridCommandEnum.Select` of a storage row).

## Master/detail grids

Master/detail grids follow `plane-dynamic.ts` (Table → Data) and `plane-design.ts` (Design Band → Properties): the master grid sets `setting: { isSelectPatch: true }`, the loader builds the detail grid (`grids[1]`) from the reloaded master's selected row (`state.rowKeys[state.selectedRowIndex]`), and the patcher answers `GridCommandEnum.Select` with a `GridPatchEnum.Grid` patch for `grids[1]` (state reset to first page, no sort/filter/selection). `gridFsp` selects the first row of the page (`selectedRowIndex` 0) if none is selected and the page has rows, so every data grid (and therefore its detail grid) starts with its first row selected, also after App.Web clears the selection on filter, sort or paging; App.Web keeps the selected row in the grid's store state (not local component state), so it follows the server and is sent with every command. Every patcher return has one entry per grid (`[{}, {}]`). A master grid's Reload must also rebuild its detail grids, so it reloads the whole plane (`/api/grid-load`); a grid no other grid depends on can set `setting: { isReloadPatch: true }` instead, which makes App.Web send `GridCommandEnum.Reload` (Reload button, paging, search) to `/api/grid-patch` and its patcher answers with a `GridPatchEnum.Grid` patch of that grid only (e.g. the `DebugPropertyDto` grid of `plane-debug-property.ts`); the grid's inputs re-render (`gridReloadCounts` in `GridStore.tsx`) without a remount. `isSelectPatch` sends `GridCommandEnum.Select` only when the selected row changes; a grid that also needs to know about a column change (`state.selectedColumnName`, otherwise only sent with the next command) sets `setting: { isSelectColumnPatch: true }`, which sends the same `Select` when the selected column changes (one request if both change; the patcher can't tell which one did), e.g. the `DebugContentDto` grid of `plane-debug-property.ts`, whose detail `DebugPropertyDto` grid shows the properties of the selected row and cell (`debugPropertyLoadByOwners` with owners `{ ownerName: 'Name/<name>/', ownerType: 'Row' }` and, if a column is selected, `{ ownerName: 'Name/<name>/ColumnName/<columnName>/', ownerType: 'Cell' }`; none with no row selected).

## Design plane

The Design plane (`plane-design.ts`, page `Design.tsx`): `DesignBandDto` rows (`contentName`, `bandEnum`, `bandName`, `sort`; `name` is `ContentName/<contentName>/BandName/<bandName>/` (`designBandName`, set on every insert/update; uniqueness only by the database index, no check in code), never sent to App.Web, the grid's rowKey is the `_id` hex; a band whose name changes does not move its properties, they stay under the old name) and their detail `PropertyDto` rows (`util-property.ts`), attached to the band by the owner `designBandPropertyOwner(band.name)` = `{ ownerName: DesignBandDto.name, ownerEnum: PropertyOwnerEnum.DesignBand }`. The Design Band grid has row Delete and multi select Delete (toolbar `DeleteMulti`) with the same confirmation dialog as the `DebugDto` grid (`gridDataDelete`/`gridDataDeleteConfirm`, shown as a modal by `Design.tsx`); `designBandDelete` also deletes the bands' properties (`propertyDeleteByOwners`). A Table band row also has a "Columns" button opening a Column Chooser like lookup (`gridDesignBandColumnsLoad`, planeName `designBandColumns`) listing the band's `DesignBandDto.columns` (`DesignBandColumnDto`: `columnName`, `isVisible`; selected if `isVisible`); its Ok (`gridDesignBandColumnsOk`) writes the selection back as `isVisible`. Opening it first syncs `columns` (`gridDesignBandColumnSync`, saved if changed) to the columns of the band's `TableName` property (`gridDynamicDataColumns` of `plane-dynamic.ts`, the columns its content view Table grid shows; all tables' if empty), in that order: missing ones added visible, ones no longer in the table removed, the others keeping `isVisible`. The content view Table grid of the band hides the columns whose `isVisible` is `false` (`ContentBandDto.hiddenColumnNames`, set by `contentBandLoad`; a column not in `columns` is visible) as `isHide` columns (the `hiddenColumnNames` parameter of `gridDynamicDataLoad`, `gridDynamicDataColumnChooserLoad` and `gridDynamicDataFilterMultiLoad`): never shown, nor offered by its Column Chooser, while a detail grid still sets its master value on them. The properties of a band are generated, not entered: each time the Properties grid is built for the selected band (Select or plane load), `designBandPropertySync` (`util-design.ts`, via `propertySync`) makes them match `DESIGN_BAND_PROPERTY_NAMES[bandEnum]` (`dto/shared/content-dto.ts`, shared so App.Web can look up property positions: Header → `Text`, Table → `Title`, `TableName`, `IsDistinct`, Form → `Title`, `RowCount`, `ColumnCount`, `TableName`) — inserts missing ones, deletes ones no longer applying, keeps the others with their `propertyValue`. Band Save does not sync, so a band has no properties until it is selected. The Properties grid shows only `propertyName` and `propertyValue` (not `name` or the owner), and only `propertyValue` is editable (`RowCount`/`ColumnCount` must be whole numbers, `IsDistinct` a bool: true/yes/1 or false/no/0, saved as `true`/`false`, or empty), there is no New (`isNewHide`), and with no band selected it has no rows. A third grid, "Design Form" (`grids[2]`, `gridDesignFormLoad`, rebuilt on plane load and on Select like the Properties grid), previews the selected band if it is a Form: `ColumnCount` header columns named by `indexToColumnNameExcel` (A, B, C, ...) and `RowCount` rows with "Hello" in every cell (each count clamped to 0..50); it is read only, with no find row, sort, paging or bar (Save/Reload), and empty for any other band. It sets `isSelectPatch`/`isSelectColumnPatch`: while one of its cells is selected (`gridDesignFormSelectedLoad`, kept on plane load if still in the form; a Design Band Select rebuilds it without selection) the Properties grid shows that cell's properties instead, owner `designFormCellPropertyOwner(band.name, rowIndex, columnName)` = `{ ownerName: band.name + 'RowIndex/<rowIndex>/ColumnName/<columnName>/', ownerEnum: PropertyOwnerEnum.DesignFormCell }`, synced by `designFormCellPropertySync` to `FieldName`, `ColumnSpan`, `RowSpan` (the spans whole numbers); `designBandDelete` also deletes them (`propertyDeleteByOwnerNameRegex`). A fourth grid, "Design Master Detail" (`grids[3]`, `gridDesignMasterDetailLoad` in `plane/plane-design-master-detail.ts`, also exporting `gridDesignMasterDetailFilterMultiLoad` for `planeDesignPatch`; no other grid depends on it), lists the `DesignMasterDetailDto` rows (`util-design-master-detail.ts`; columns `contentName`, `bandNameMaster`, `fieldNameMaster`, `bandNameDetail`, `fieldNameDetail`, `isActive` ("Is Active", `true`/`false`, also accepting yes/no/1/0, empty is `false`), all editable) and is built like the Design Band grid: bar (New, Save, Reload, pager), row Delete and multi select Delete (toolbar `DeleteMulti`, `isSelectMultiPatch`) with the same `gridDataDeleteConfirm` dialog (`Design.tsx` shows it as a modal at `[3, 1, 0]`; built by `gridDataLoad`, its `save` hook doing the cycle check), find row and Filter Multi. Its Save writes nothing and throws (an Error alert) if the saved rows would make the active Design Master Details of a content circular (`designMasterDetailCycle`, a band being its own master included). `Design.tsx` shows the Design Band, Design Master Detail and Design Form grids (in this order) in the main column and the Properties grid in a right hand sidebar (`sidebarRightClassName`, below the other grids on narrower screens than `lg`).

## Content and the contentView plane

A content is the `DesignBandDto` rows of one `contentName`: `contentApi(request, dto)` (`util-content.ts`, signed-in only) returns them as a `ContentDto` (`dto/shared/content-dto.ts`, with `ContentBandDto` and `ContentBandEnum`), served by `api/content.ts` (`POST` `ContentRequestDto`, passed to `contentApi` as is). Each `ContentBandDto.propertyValues` holds the band's `PropertyDto.propertyValue`s positionally, in `DESIGN_BAND_PROPERTY_NAMES[bandEnum]` order (`''` if missing, e.g. a band never selected). App.Web renders it with the `Content.tsx` component (`<Content contentName="A" />`, e.g. on the Content page `page/Content.tsx`, component `ContentPage`), looking values up by name via `contentBandPropertyValue(band, propertyName)` (`content-dto.ts`, also used by the backend): Header renders as `<h1>` with its `Text`; all Table and Form bands share ONE plane, `CONTENT_VIEW_PLANE_NAME` (`contentView`, `planeContentViewLoad`/`planeContentViewPatch` in `plane/plane-content-view.ts`), in the component's own `GridStoreProvider` (not the Layout store): after `/api/content`, `Content.tsx` calls `load(planeName, grids)` with one grid per Table/Form band in band order (`grids[i]` the i-th of them), each carrying only its band's name (`ContentBandDto.name`) in `GridStateDto.custom[CONTENT_VIEW_CUSTOM_BAND_NAME]`; the server reads the bands and their properties from the database on every request (`contentViewBandLoad` in `util-content-view.ts`, via `contentBandLoad`), so no property value is sent by App.Web. Every command reloads the whole plane, the grids built in the order of `gridContentViewBuildOrder`: the grid with a command first (e.g. a Form Save writing `DynamicDto` rows a Table of the same `TableName` shows), then every master grid before its detail grids (see below), otherwise in band order (also the fallback for a cycle of Design Master Details), each returned at its own index and titled (`GridDto.title`) by its band's `Title` property (its `TableName` if empty, no title if both are empty) and, if its band is the master band of a Design Master Detail (`DesignMasterDetailDto.contentName` + `bandNameMaster` → `designBandName`), with `setting: { isSelectPatch: true }` (otherwise no setting, replacing any sent by App.Web); a missing band or other band is an empty grid keeping its `custom`. Master values are not kept in the grid state: a grid whose band is the detail band of a Design Master Detail (`bandNameDetail`) whose master band is the band of another grid of the plane shows only the `DynamicDto` rows whose `fieldNameDetail` equals the `fieldNameMaster` value of the master grid's selected row, loaded by id (`dynamicLoadByIds` of `state.rowKeys[state.selectedRowIndex]`) on every request (`gridContentViewDetail`, its `rowFilter` passed to `gridDynamicDataLoad`/`gridDynamicDataFilterMultiLoad` and `gridContentFormLoad`; no rows if the master has no row selected), and every row it inserts gets that master value as its `fieldNameDetail` (its `newValues`, shown as a label instead of a text box in the New row or form repetition, set by Save insert over any modify of that field); the master grid already built gives its reloaded selection, otherwise (the detail has the command, or a cycle) the one sent by App.Web. A Design Master Detail only takes effect if `isActive` is `true` (missing counts as `false`) and both `fieldNameMaster` and `fieldNameDetail` are set (`designMasterDetailBands` in `util-design-master-detail.ts`). A master grid's `GridCommandEnum.Select` (`isSelectPatch`) is answered by `planeContentViewPatch` with a `GridPatchEnum.Grid` patch of each of its detail grids (`gridContentViewSelectPatch`: rebuilt with the master's new selection, state reset to first page, no sort/filter/selection; a detail grid that is itself a master rebuilds its own detail grids the same way, each grid once).

Table renders the Dynamic page's "Data" grid (`gridDynamicDataLoad`, exported by `plane-dynamic.ts` with `gridDynamicDataFilterMultiLoad` and `gridDynamicDataColumnChooserLoad` for the patcher's Filter Multi and Column Chooser) filtered by its `TableName` (all rows if empty), with a toolbar Column Chooser button (`isColumnChooser`, not on the Dynamic page) showing only the chosen columns (`GridStateDto.columnNames`, kept by a master's Select). If its `IsDistinct` property is `true` it shows one row per distinct combination of the shown columns' texts (`gridDynamicDataDistinct`, before Filter Multi and `gridFsp`, so paging counts distinct rows), its rowKey the `_id` of any (the first) row of that key group (so a master's selection gives the `fieldNameMaster` value of that row, the same for the whole group if it is a shown column); its cells are read-only labels and it has no New (`isNewHide`).

Form renders (`gridContentFormLoad` in `plane-content-view.ts`) `ColumnCount` header columns named by `indexToColumnNameExcel` and `RowCount` rows, each cell showing its Design Form cell `FieldName` property (owner `designFormCellPropertyOwner`, all of the band loaded by `designFormCellPropertyLoadAll`) or "Cell" if missing or empty, each such row followed by a row of their values (a text box (`GridCellEnum.Edit`) with the value of that `FieldName` of the `DynamicDto` row, the label "Empty" if the cell has no `FieldName`; the text box's `columnName` is that `FieldName` (not A, B, ..., which repeat for every form row, while a modify is identified by `rowIndex` and `columnName`)), the whole form repeated for each `DynamicDto` row of the current page, every cell's `rowIndex` being that row's index on the page (the first one selected by `gridFsp` like any data grid; `state.rowKeys` are the rows' `_id` hex, like the Data grid) (each count clamped to 0..50 by `designFormCount`, exported by `plane-design.ts`, empty or invalid is 0), followed by the bar (New, Save, Reload, pager); the pager pages (`gridFsp`) the `DynamicDto` rows of its `TableName` (all rows if empty, like the Dynamic page's "Data" grid), Save (`gridDataSaveUpdate` with a `gridDynamicDataColumn` per `FieldName`) writes the modified text boxes into their `DynamicDto` rows (`rowKeys`; only columnNames that are a `FieldName` of the form), and, like the Debug Data grid (`gridDataNew`), New appends one empty form repetition (`isNew` text boxes, `rowIndex` after the page's rows) which Save (`gridDataSaveInsert`) inserts as a `DynamicDto` row with its `TableName`; other bands still show only their enum number.
