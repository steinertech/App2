# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

SPA application deployed as two independent Vercel projects:
- `App.Web` — React SPA frontend (Vite)
- `App.Server` — TypeScript backend deployed as Vercel serverless functions (no bundler; each file under `api/` is deployed as-is)

## Commands

### App.Web
```
cd App.Web
pnpm install
pnpm run dev       # start Vite dev server
pnpm run build     # tsc && vite build
pnpm run preview   # preview the production build
```

### App.Server
```
cd App.Server
pnpm install
```
There is no build/dev/test/lint script for `App.Server` — files under `api/` are deployed directly by Vercel as serverless functions. Requires a `MONGODB_URI` environment variable at runtime (see `util/util-db.ts`). A `tsconfig.json` (with `@types/node`) is present purely for editor/type-checking support — run `pnpm exec tsc --noEmit` to typecheck the package; it is not part of the deploy or any pnpm script.

`App.Server/package.json` has `"type": "module"`, and Node's ESM resolver (unlike CommonJS) doesn't guess file extensions, so **every relative import in `App.Server` must include an explicit `.js` extension** (e.g. `import { corsHeaders } from '../util/util-main.js';`), even though the source files are `.ts`. Omitting the extension breaks at runtime with `ERR_MODULE_NOT_FOUND` since there is no build step to catch it beforehand.

There is no test suite or linter configured in this repository.

## Architecture

### Two separately deployed apps, stitched together via rewrites
`App.Web` and `App.Server` are deployed as separate Vercel projects and glued together purely through `vercel.json` rewrites:
- `App.Web/vercel.json` rewrites `/api/*` to the deployed `App.Server` URL, and everything else to `/index.html` (SPA fallback).
- `App.Server/vercel.json` rewrites `/` to `/api`.

Vite only builds `App.Web`; `App.Server` has no build step.

### App.Server endpoint pattern
Every file in `App.Server/api/` is a standalone Vercel function, mapped by filename to `/api/<filename>` (e.g. `api/user.ts` → `/api/user`). Each file's default export is `apiHandler(method, handler)` from `util-main.ts` (it returns the `{ fetch(request) }` object Vercel expects):
1. `method` is the single HTTP method the endpoint accepts: `'POST'` for every endpoint except `api/index.ts` (the plain-text page at the server root), which is `'GET'`. A POST body is always an `ApiRequestDto<T>` (`dto/shared/api-request-dto.ts`: `{ data, versionClient?, language?, requestCount? }`; App.Web's `apiFetch` increases `requestCount` by 1 on every call), parsed once by `apiHandler` (bad JSON → 500); handlers read their own request DTO with `requestData<T>(request)` and never call `request.json()`, and the language with `requestLanguage(request)` (falls back to `Accept-Language`). If `versionClient` differs from `VERSION_SERVER` (e.g. during a deploy of only one of the two apps), `apiHandler` adds a Warning alert asking to reload the page. The session cookie and `Origin`/`Referer` (`domainName`, `sectorKey`) deliberately stay outside the body. `apiHandler` answers `OPTIONS` with 204, rejects any other method with 405 (plus an `Allow` header), and merges `corsHeaders(request, method)` into every response — handlers never deal with OPTIONS or CORS themselves. If `handler` throws, `apiHandler` logs the error, queues its message as an `AlertEnum.Error` alert and returns a 500 with `data: null` (so a plain `throw new Error('...')` reaches the user as an alert).
2. `handler` delegates business logic to a function in `App.Server/util/`.
3. `handler` returns its result via `jsonResponse(data, status?, headers?)`, which returns a plain `ApiResult` (not a `Response`); `apiHandler` sends it as an `ApiResponseDto<T>` (`dto/shared/api-response-dto.ts`: `{ data, alerts?, redirectUrl?, responseCount? }`, `responseCount` being the request's `requestCount`), the envelope of every JSON response. A handler returning a plain `Response` (only `api/index.ts`, plain text) is sent as is, without alerts or redirect url.

Shared logic lives in `App.Server/util/` (not directly in `api/`):
- `util-main.ts` — `VERSION_SERVER`, `domainName(request)`, `sectorKeyDb(request, type)`, `sectorKeyProjectDb(request, type)`, `sectorKeyStorage(request)`, `sectorKeyProjectStorage(request)`, `corsHeaders(request, method)`, `jsonResponse(...)`/`ApiResult`, `apiHandler(method, handler)`, `alertAdd(request, alertEnum, text)`, `redirectSet(request, url)`
- `util-db.ts` — the shared MongoDB `client` (via `@vercel/functions` `attachDatabasePool`) and `DB_NAME` (`myDatabase`; always `client.db(DB_NAME)`, never `client.db()`, which would use the `MONGODB_URI` path or `test`); creates the unique index `{ sectorKey: 1, name: 1 }` on `myCollection` (errors only logged)
- `util-user.ts` — user sign-up/sign-in/session/sign-out
- `util-debug.ts` — `DebugDto` load/insert/update/delete (`dto/debug-dto.ts`)
- `util-debug-property.ts` — `DebugContentDto` load/insert/update/delete and `DebugPropertyDto` load/insert/update (`dto/debug-property-dto.ts`)
- `util-property.ts` — generic `PropertyDto` load/load by owners/load by ids/insert/update and `propertySync(request, owner, propertyNames)` (`dto/property-dto.ts`; a property is attached to an owner `{ ownerName, ownerEnum }`, `ownerEnum` being a `PropertyOwnerEnum` (`dto/property-dto.ts`), its `name` is `ownerName + 'OwnerEnum/<ownerEnum name>/PropertyName/<propertyName>/'` by `propertyDtoName`; project sector, `sectorKeyProjectDb(request, 'PropertyDto')`, so sign-in and a selected project are required). Owner-specific logic stays with the owner, e.g. design band properties in `util-design.ts`
- `util-content.ts` — `loadContent(request, contentName)` and `contentBandLoad(request, bands)` (`DesignBandDto` rows → `ContentBandDto` with their property values)
- `util-content-view.ts` — `contentViewBandLoad(request, bandNames)`: the bands (by `DesignBandDto.name`) the `contentView` plane's grids are built from
- `util-design-master-detail.ts` — `DesignMasterDetailDto` (`dto/design-master-detail-dto.ts`) `designMasterDetailName`/load/load by ids/insert/update/delete (project sector, `sectorKeyProjectDb(request, 'DesignMasterDetailDto')`; `name` set on every insert/update)
- `util-storage.ts` — blob upload/download via `@vercel/blob` (blob paths are prefixed with `sectorKeyProjectStorage(request)`)
- `util-grid.ts` — shared grid helpers plus the plane registry (`PLANE_LOADERS`, `PLANE_GRID_PATCHERS`) behind `api/grid-load.ts` / `api/grid-patch.ts`

Grid-specific logic lives in `App.Server/grid/` — one file per plane served to App.Web (`grid-project.ts` with the project and user grids, `grid-debug.ts` with the Debug page's single `DebugDto` grid ("Debug Data"), `grid-debug-property.ts` with the Debug Property page's (plane `debugProperty`) master `DebugContentDto` grid ("Debug Content", built like the `DebugDto` grid and reusing its exported `gridDebugDeleteConfirm`/`gridDebugNew`) and its detail `DebugPropertyDto` grid ("Debug Property"; New, edit and Save only: no Column Chooser or Delete) and a third grid "Debug Table" (`grids[2]`, `gridDebugTableLoad`, rebuilt on plane load, Select and the Debug Property grid's Reload): if the `ownerType` `Row` properties of the selected row have a whole-number `RowCount` and `ColumnCount` (each clamped to 0..50), that many rows of read-only "Empty" label cells under header columns named by `indexToColumnNameExcel`, otherwise empty; it sets `isSelectPatch`/`isSelectColumnPatch`, and while one of its cells is selected the Debug Property grid shows that cell's properties instead (`gridDebugPropertyOwners`: owner `{ ownerName: 'RowIndex/<rowIndex>/ColumnName/<columnName>/', ownerType: 'CellTable' }`, also used by plane load, Reload and Filter Multi; a Debug Content Select rebuilds the table without selection), `grid-storage.ts` including the Image Preview grid, `grid-schema.ts`, `grid-dynamic.ts`, `grid-design.ts`, `grid-content-view.ts` with the `contentView` plane of the `Content.tsx` component (one grid per Table/Form band), plus `grid-design-master-detail.ts` with the Design plane's Design Master Detail grid, used by `grid-design.ts`). Each plane has one loader `(request, gridPlaneDto) => Promise<GridPlaneDto>` registered in `PLANE_LOADERS` in `util/util-grid.ts` (it also builds any grid depending on another grid of the plane, e.g. the Image Preview of the selected storage row), and optionally one patcher of the same signature in `PLANE_GRID_PATCHERS` (returns `GridDto.patches` per grid, `grids[i]` for the incoming `grids[i]`; a `GridPatchEnum.Grid` patch replaces or removes that whole grid, e.g. the Image Preview after `GridCommandEnum.Select` of a storage row).

Master/detail grids follow `grid-dynamic.ts` (Table → Data) and `grid-design.ts` (Design Band → Properties): the master grid sets `setting: { isSelectPatch: true }`, the loader builds the detail grid (`grids[1]`) from the reloaded master's selected row (`state.rowKeys[state.selectedRowIndex]`), and the patcher answers `GridCommandEnum.Select` with a `GridPatchEnum.Grid` patch for `grids[1]` (state reset to first page, no sort/filter/selection). `gridFsp` selects the first row of the page (`selectedRowIndex` 0) if none is selected and the page has rows, so every data grid (and therefore its detail grid) starts with its first row selected, also after App.Web clears the selection on filter, sort or paging; App.Web keeps the selected row in the grid's store state (not local component state), so it follows the server and is sent with every command. Every patcher return has one entry per grid (`[{}, {}]`). A master grid's Reload must also rebuild its detail grids, so it reloads the whole plane (`/api/grid-load`); a grid no other grid depends on can set `setting: { isReloadPatch: true }` instead, which makes App.Web send `GridCommandEnum.Reload` (Reload button, paging, search) to `/api/grid-patch` and its patcher answers with a `GridPatchEnum.Grid` patch of that grid only (e.g. the `DebugPropertyDto` grid of `grid-debug-property.ts`); the grid's inputs re-render (`gridReloadCounts` in `GridStore.tsx`) without a remount. `isSelectPatch` sends `GridCommandEnum.Select` only when the selected row changes; a grid that also needs to know about a column change (`state.selectedColumnName`, otherwise only sent with the next command) sets `setting: { isSelectColumnPatch: true }`, which sends the same `Select` when the selected column changes (one request if both change; the patcher can't tell which one did), e.g. the `DebugContentDto` grid of `grid-debug-property.ts`, whose detail `DebugPropertyDto` grid shows the properties of the selected row and cell (`debugPropertyLoadByOwners` with owners `{ ownerName: 'Name/<name>/', ownerType: 'Row' }` and, if a column is selected, `{ ownerName: 'Name/<name>/ColumnName/<columnName>/', ownerType: 'Cell' }`; none with no row selected).

The Design plane (`grid-design.ts`, page `Design.tsx`): `DesignBandDto` rows (`contentName`, `bandEnum`, `bandName`, `sort`; `name` is `ContentName/<contentName>/BandName/<bandName>/` (`designBandName`, set on every insert/update; uniqueness only by the database index, no check in code), never sent to App.Web, the grid's rowKey is the `_id` hex; a band whose name changes does not move its properties, they stay under the old name) and their detail `PropertyDto` rows (`util-property.ts`), attached to the band by the owner `designBandPropertyOwner(band.name)` = `{ ownerName: DesignBandDto.name, ownerEnum: PropertyOwnerEnum.DesignBand }`. The Design Band grid has row Delete and multi select Delete (toolbar `DeleteMulti`) with the same confirmation dialog as the `DebugDto` grid (`gridDebugDeleteConfirm`, shown as a modal by `Design.tsx`); `designBandDelete` also deletes the bands' properties (`propertyDeleteByOwners`). A Table band row also has a "Columns" button opening a Column Chooser like lookup (`gridDesignBandColumnsLoad`, planeName `designBandColumns`) listing the band's `DesignBandDto.columns` (`DesignBandColumnDto`: `columnName`, `isVisible`; selected if `isVisible`); its Ok (`gridDesignBandColumnsOk`) writes the selection back as `isVisible`. Opening it first syncs `columns` (`gridDesignBandColumnSync`, saved if changed) to the columns of the band's `TableName` property (`gridDynamicDataColumns` of `grid-dynamic.ts`, the columns its content view Table grid shows; all tables' if empty), in that order: missing ones added visible, ones no longer in the table removed, the others keeping `isVisible`. The content view Table grid of the band hides the columns whose `isVisible` is `false` (`ContentBandDto.hiddenColumnNames`, set by `contentBandLoad`; a column not in `columns` is visible) as `isHide` columns (the `hiddenColumnNames` parameter of `gridDynamicDataLoad`, `gridDynamicDataColumnChooserLoad` and `gridDynamicDataFilterMultiLoad`): never shown, nor offered by its Column Chooser, while a detail grid still sets its master value on them. The properties of a band are generated, not entered: each time the Properties grid is built for the selected band (Select or plane load), `designBandPropertySync` (`util-design.ts`, via `propertySync`) makes them match `DESIGN_BAND_PROPERTY_NAMES[bandEnum]` (`dto/shared/content-dto.ts`, shared so App.Web can look up property positions: Header → `Text`, Table → `Title`, `TableName`, `IsDistinct`, Form → `Title`, `RowCount`, `ColumnCount`, `TableName`) — inserts missing ones, deletes ones no longer applying, keeps the others with their `propertyValue`. Band Save does not sync, so a band has no properties until it is selected. The Properties grid shows only `propertyName` and `propertyValue` (not `name` or the owner), and only `propertyValue` is editable (`RowCount`/`ColumnCount` must be whole numbers, `IsDistinct` a bool: true/yes/1 or false/no/0, saved as `true`/`false`, or empty), there is no New (`isNewHide`), and with no band selected it has no rows. A third grid, "Design Form" (`grids[2]`, `gridDesignFormLoad`, rebuilt on plane load and on Select like the Properties grid), previews the selected band if it is a Form: `ColumnCount` header columns named by `indexToColumnNameExcel` (A, B, C, ...) and `RowCount` rows with "Hello" in every cell (each count clamped to 0..50); it is read only, with no find row, sort, paging or bar (Save/Reload), and empty for any other band. It sets `isSelectPatch`/`isSelectColumnPatch`: while one of its cells is selected (`gridDesignFormSelectedLoad`, kept on plane load if still in the form; a Design Band Select rebuilds it without selection) the Properties grid shows that cell's properties instead, owner `designFormCellPropertyOwner(band.name, rowIndex, columnName)` = `{ ownerName: band.name + 'RowIndex/<rowIndex>/ColumnName/<columnName>/', ownerEnum: PropertyOwnerEnum.DesignFormCell }`, synced by `designFormCellPropertySync` to `FieldName`, `ColumnSpan`, `RowSpan` (the spans whole numbers); `designBandDelete` also deletes them (`propertyDeleteByOwnerNameRegex`). A fourth grid, "Design Master Detail" (`grids[3]`, `gridDesignMasterDetailLoad` in `grid/grid-design-master-detail.ts`, also exporting `gridDesignMasterDetailFilterMultiLoad` for `planeDesignPatch`; no other grid depends on it), lists the `DesignMasterDetailDto` rows (`util-design-master-detail.ts`; columns `contentName`, `bandNameMaster`, `fieldNameMaster`, `bandNameDetail`, `fieldNameDetail`, `isActive` ("Is Active", `true`/`false`, also accepting yes/no/1/0, empty is `false`), all editable) and is built like the Design Band grid: bar (New, Save, Reload, pager), row Delete and multi select Delete (toolbar `DeleteMulti`, `isSelectMultiPatch`) with the same `gridDebugDeleteConfirm` dialog (`Design.tsx` shows it as a modal at `[3, 1, 0]`), find row and Filter Multi. Its Save writes nothing and throws (an Error alert) if the saved rows would make the active Design Master Details of a content circular (`designMasterDetailCycle`, a band being its own master included). `Design.tsx` shows the Design Band, Design Master Detail and Design Form grids (in this order) in the main column and the Properties grid in a right hand sidebar (`sidebarRightClassName`, below the other grids on narrower screens than `lg`).

A content is the `DesignBandDto` rows of one `contentName`: `loadContent(request, contentName)` (`util-content.ts`, signed-in only) returns them as a `ContentDto` (`dto/shared/content-dto.ts`, with `ContentBandDto` and `ContentBandEnum`), served by `api/content.ts` (`POST` `ContentRequestDto`). Each `ContentBandDto.propertyValues` holds the band's `PropertyDto.propertyValue`s positionally, in `DESIGN_BAND_PROPERTY_NAMES[bandEnum]` order (`''` if missing, e.g. a band never selected). App.Web renders it with the `Content.tsx` component (`<Content contentName="A" />`, e.g. on the Content page `page/Content.tsx`, component `ContentPage`), looking values up by name via `contentBandPropertyValue(band, propertyName)` (`content-dto.ts`, also used by the backend): Header renders as `<h1>` with its `Text`; all Table and Form bands share ONE plane, `CONTENT_VIEW_PLANE_NAME` (`contentView`, `planeContentViewLoad`/`planeContentViewPatch` in `grid/grid-content-view.ts`), in the component's own `GridStoreProvider` (not the Layout store): after `/api/content`, `Content.tsx` calls `load(planeName, grids)` with one grid per Table/Form band in band order (`grids[i]` the i-th of them), each carrying only its band's name (`ContentBandDto.name`) in `GridStateDto.custom[CONTENT_VIEW_CUSTOM_BAND_NAME]`; the server reads the bands and their properties from the database on every request (`contentViewBandLoad` in `util-content-view.ts`, via `contentBandLoad` of `util-content.ts`), so no property value is sent by App.Web. Every command reloads the whole plane, the grids built in the order of `gridContentViewBuildOrder`: the grid with a command first (e.g. a Form Save writing `DynamicDto` rows a Table of the same `TableName` shows), then every master grid before its detail grids (see below), otherwise in band order (also the fallback for a cycle of Design Master Details), each returned at its own index and titled (`GridDto.title`) by its band's `Title` property (its `TableName` if empty, no title if both are empty) and, if its band is the master band of a Design Master Detail (`DesignMasterDetailDto.contentName` + `bandNameMaster` → `designBandName`), with `setting: { isSelectPatch: true }` (otherwise no setting, replacing any sent by App.Web); a missing band or other band is an empty grid keeping its `custom`. Master values are not kept in the grid state: a grid whose band is the detail band of a Design Master Detail (`bandNameDetail`) whose master band is the band of another grid of the plane shows only the `DynamicDto` rows whose `fieldNameDetail` equals the `fieldNameMaster` value of the master grid's selected row, loaded by id (`dynamicLoadByIds` of `state.rowKeys[state.selectedRowIndex]`) on every request (`gridContentViewDetail`, its `rowFilter` passed to `gridDynamicDataLoad`/`gridDynamicDataFilterMultiLoad` and `gridContentFormLoad`; no rows if the master has no row selected), and every row it inserts gets that master value as its `fieldNameDetail` (its `newValues`, shown as a label instead of a text box in the New row or form repetition, set by Save insert over any modify of that field); the master grid already built gives its reloaded selection, otherwise (the detail has the command, or a cycle) the one sent by App.Web. A Design Master Detail only takes effect if `isActive` is `true` (missing counts as `false`) and both `fieldNameMaster` and `fieldNameDetail` are set (`designMasterDetailBands` in `util-design-master-detail.ts`). A master grid's `GridCommandEnum.Select` (`isSelectPatch`) is answered by `planeContentViewPatch` with a `GridPatchEnum.Grid` patch of each of its detail grids (`gridContentViewSelectPatch`: rebuilt with the master's new selection, state reset to first page, no sort/filter/selection; a detail grid that is itself a master rebuilds its own detail grids the same way, each grid once). Table renders the Dynamic page's "Data" grid (`gridDynamicDataLoad`, exported by `grid-dynamic.ts` with `gridDynamicDataFilterMultiLoad` and `gridDynamicDataColumnChooserLoad` for the patcher's Filter Multi and Column Chooser) filtered by its `TableName` (all rows if empty), with a toolbar Column Chooser button (`isColumnChooser`, not on the Dynamic page) showing only the chosen columns (`GridStateDto.columnNames`, kept by a master's Select). If its `IsDistinct` property is `true` it shows one row per distinct combination of the shown columns' texts (`gridDynamicDataDistinct`, before Filter Multi and `gridFsp`, so paging counts distinct rows), its rowKey the `_id` of any (the first) row of that key group (so a master's selection gives the `fieldNameMaster` value of that row, the same for the whole group if it is a shown column); its cells are read-only labels and it has no New (`isNewHide`). Form renders (`gridContentFormLoad` in `grid-content-view.ts`) `ColumnCount` header columns named by `indexToColumnNameExcel` and `RowCount` rows, each cell showing its Design Form cell `FieldName` property (owner `designFormCellPropertyOwner`, all of the band loaded by `designFormCellPropertyLoadAll`) or "Cell" if missing or empty, each such row followed by a row of their values (a text box (`GridCellEnum.Edit`) with the value of that `FieldName` of the `DynamicDto` row, the label "Empty" if the cell has no `FieldName`; the text box's `columnName` is that `FieldName` (not A, B, ..., which repeat for every form row, while a modify is identified by `rowIndex` and `columnName`)), the whole form repeated for each `DynamicDto` row of the current page, every cell's `rowIndex` being that row's index on the page (the first one selected by `gridFsp` like any data grid; `state.rowKeys` are the rows' `_id` hex, like the Data grid) (each count clamped to 0..50 by `designFormCount`, exported by `grid-design.ts`, empty or invalid is 0), followed by the bar (New, Save, Reload, pager); the pager pages (`gridFsp`) the `DynamicDto` rows of its `TableName` (all rows if empty, like the Dynamic page's "Data" grid), Save (`gridContentFormSaveUpdate`) writes the modified text boxes into their `DynamicDto` rows (`rowKeys`; only columnNames that are a `FieldName` of the form), and, like the Debug Data grid (`gridDebugNew`), New appends one empty form repetition (`isNew` text boxes, `rowIndex` after the page's rows) which Save (`gridContentFormSaveInsert`) inserts as a `DynamicDto` row with its `TableName`; other bands still show only their enum number.

DTOs (plain interfaces, not classes) live under `App.Server/dto/`, split by whether `App.Web` uses them:
- `App.Server/dto/shared/` — DTOs used by both `App.Server` and `App.Web` (must have no Node-only fields such as `ObjectId`). `App.Web` and `App.Server` share the same git repo, so these are imported directly by `App.Web` via a relative path (`import type { GridDto } from '../../../App.Server/dto/shared/grid-dto.ts'`) instead of being duplicated.
- `App.Server/dto/` (top level) — backend-only DTOs (`ProjectDto`, `DebugDto`, `DebugPropertyDto`, `DebugContentDto`, `PropertyDto`, `SessionDto`, `UserDto`, `DesignBandDto`, `DesignMasterDetailDto`, `GridConfigDto`, `StorageFileDto`). `App.Web` never imports from here — those carrying `ObjectId` couldn't be imported anyway, since `ObjectId` isn't installed in `App.Web` (and serializes to a plain string over JSON). They reach the frontend only indirectly, e.g. converted into a `GridDto` by `util-grid.ts`.

New DTOs go in `dto/shared/` only if `App.Web` actually imports them (and they have no `ObjectId` or other Node-only field); otherwise directly in `dto/`.

### App version
The app version is stored in two places: `VERSION_CLIENT` in `App.Web/src/util/util-main.ts` and `VERSION_SERVER` in `App.Server/util/util-main.ts`. **Both values must always be identical** — whenever one is bumped, bump the other to the same value in the same change. (`App.Web/src/page/About.tsx` displays both side by side.)

### Single-collection MongoDB pattern
All persisted DTOs (`UserDto`, `SessionDto`, `ProjectDto`, `DebugDto`, `DebugPropertyDto`, `DebugContentDto`, `PropertyDto`, `DesignBandDto`, `DesignMasterDetailDto` — the ones with `_id`/`type` fields; not e.g. `GridConfigDto` or `StorageFileDto`) are stored in one MongoDB collection (`'myCollection'`), disambiguated by a `type` field (e.g. `type: 'UserDto'`) and scoped by a `sectorKey` field. They all extend `DbDto` (`dto/db-dto.ts`: `_id`, `sectorKey`, `type`, `name` — `name` being the document's unique key within its `sectorKey` (which includes the type, so unique per type) — enforced by a unique index `{ sectorKey: 1, name: 1 }` on the database, created by `util-db.ts` on every cold start; every derived DTO redeclares `name` with a comment on how it is built). A name calculated by the backend is a path like `sectorKey`: description/value segment pairs, each followed by `/`, e.g. `ContentName/A/BandName/Header/` (`designBandName`), `TableName/<tableName>/ColumnName/<columnName>/`, `Domain/<domainName>/Email/<email>/`, `SessionId/<uuid>/`, `Id/<uuid>/` (`DynamicDto`). A name built on another name (e.g. a property's `ownerName`) appends further pairs to it (`ContentName/A/BandName/Form/RowIndex/0/ColumnName/B/OwnerEnum/DesignFormCell/PropertyName/FieldName/`), so it must end with `/`; a user-entered name (e.g. `DebugContentDto.name`) gets its own description segment first (`Name/<name>/`). Names entered by the user (`DebugDto`, `DebugContentDto`, `ProjectDto`) are plain values. Adding a new entity means adding a new DTO interface extending `DbDto` plus a `type` discriminator, not a new collection. `DynamicDto` (`dto/dynamic-dto.ts`) keeps its user-defined column values (the `SchemaDto.columnName`s of its `tableName`, e.g. A, B; also a Form's `FieldName`s and a Design Master Detail's `fieldNameMaster`/`fieldNameDetail`) in `values`, apart from its static fields (`_id`, `name`, `sectorKey`, `type`, `tableName`), so a column name never collides with one of them; the Data grid reads a dynamic column through `GridConfigColumnDto.rowToValue` (`gridRowValue` in `util-grid.ts`, used by `gridFsp` and Filter Multi) and writes it with `gridDynamicDataValueSet`.

### sectorKey scoping
`sectorKey(request, isProject)` in `util-main.ts` (not exported) builds the base key used for both persistence layers:
- **MongoDB** — never directly: a document's `sectorKey` field (also its query filter) is built with `sectorKeyDb(request, type)` (global, e.g. `util-user.ts`, `util-project.ts`) or `sectorKeyProjectDb(request, type)` (project, e.g. `util-property.ts`), which append `Type/<type>/` (`type` being the DTO interface name, the same as its `type` field, e.g. `'UserDto'`) to `sectorKey(request, false|true)`, so e.g. `Domain/<domainName>/Global/Type/UserDto/`.
- **Blob storage** — never directly: the path prefix of every blob is built with `sectorKeyStorage(request)` (global) or `sectorKeyProjectStorage(request)` (project; `util-storage.ts` builds `sectorKeyProjectStorage(request) + path`), which append `Storage/` to `sectorKey(request, false|true)`, so files live under `Domain/<domainName>/Project/<projectName>/Storage/...`.

The key takes one of two forms:
- `Domain/<domainName>/Global/` when `isProject` is `false` (e.g. users, projects — looked up by domain, no sign-in required)
- `Domain/<domainName>/Project/<projectName>/` when `isProject` is `true` (e.g. blob files inside a project) — this branch also asserts the caller has a valid session (throws `'User not signed in!'` if not, after `redirectSet(request, '/sign-in')`) and a selected project (`<projectName>` is the session's `projectName`, which mirrors `UserDto.projectName`; throws `'User has no project selected!'` if unset), so `isProject: true` is how sign-in is enforced for a query or blob access.

Always build sector keys through `sectorKeyDb`/`sectorKeyProjectDb` (MongoDB documents) or `sectorKeyStorage`/`sectorKeyProjectStorage` (blobs) rather than constructing the `Domain/.../Global|Project/` string manually.

### Alert messages
Any backend code with access to the `request` can call `alertAdd(request, AlertEnum.Success | Info | Warning | Error, text)` (`util-main.ts`; `AlertEnum`/`AlertDto` in `dto/shared/alert-dto.ts`). `apiHandler` sends the queued alerts in `ApiResponseDto.alerts` (also on a 500). On App.Web, `apiFetch<T>(path, data?, init?)` (`src/util/util-main.ts`; always a POST of `data` wrapped in an `ApiRequestDto` with `VERSION_CLIENT` and the language of the current url, `init` only for e.g. `credentials`) calls `addAlert(...)` for them (plus a generic Error alert if the status is not ok and none was sent) and returns `ApiResponseDto.data` typed as `T`, or `undefined` if the status is not ok (it rethrows if no response arrives), so callers never read `response.ok`/`response.json()`; `NavState` shows the top alert with a close button (`removeAlert()`) and a count of open alerts. Frontend-only alerts can be added with `addAlert(...)` directly.

### Redirect url
The same way, backend code can call `redirectSet(request, url)` (`util-main.ts`) to make App.Web navigate after the call. Only ONE url per request (a later call overwrites an earlier one); `url` is a language neutral App.Web path such as `'/'`. `apiHandler` sends it in `ApiResponseDto.redirectUrl`. `apiFetch` reads it and calls `redirect(url)`, which dispatches a window event; `NavState` (inside the router) navigates there, adding the current language prefix (`/de`). Used e.g. after a successful SignIn to go to the Home page.

### Session handling
All user calls go through a single endpoint, `api/user.ts` (`/api/user`): App.Web always sends a `POST` with a `UserRequestDto` whose `requestEnum` (`UserRequestEnum` in `dto/shared/user-request-dto.ts`: `SignUp`, `SignIn`, `SignOut`, `Session`) selects the operation; `None` or an unknown value returns 400. App.Web calls it through `userRequest(dto)` in `NavState.tsx`. Responses (`UserResponseDto`) never include `sessionId`.

SignIn (`UserRequestEnum.SignIn` → `signIn`) sets an httpOnly `sessionId` cookie. `userSession(request)` (in `util-user.ts`) reads that cookie and looks up the matching `SessionDto` with `isSignIn: true`. `signOut` flips `isSignIn` to `false` rather than deleting the session document.

### App.Web routing and page structure
`App.Web/src/main.tsx` defines all routes with `react-router-dom`'s `<Routes>`/`<Route>`, wrapped in a shared `<Layout>` (`Nav` + `NavState` bar + `<Outlet>`). Any component mounted at a route `path` lives in `App.Web/src/page/`; shared/non-routed components (`Layout.tsx`, `Content.tsx`, `Nav.tsx`, `Grid.tsx`, `NavState.tsx`) stay directly in `App.Web/src/`. `apiUrl` (the `/api/` prefix used for all backend calls) is exported from `src/page/App.tsx`.

Second level navigation uses a layout route rendering `Sidebar.tsx` next to an `<Outlet>`: `page/DebugLayout.tsx` (Debug, Debug Property under `/debug/...`) and `page/SchemaLayout.tsx` (Schema, Dynamic, Design, Content, a pathless layout route keeping their own paths `/schema`, `/dynamic`, `/design`, `/content`). Only the first page of a group is in the `Nav` bar; its link is also active on the group's other pages (`subPaths` in `Nav.tsx`). Pages inside such a layout don't wrap themselves in `container` (the layout does).

`main.tsx` renders in `<StrictMode>`, which runs every effect twice in dev. A page that calls the backend on mount (e.g. `load('storage')`, sign-out) uses `useEffectOnce(effect, deps)` (`src/util/util-main.ts`) instead of `useEffect`, so the call is sent once per distinct `deps` values.

`NavState.tsx` polls `/api/user` (`UserRequestEnum.Session`) on mount and exposes `refreshNavState()`, which dispatches a window event other components (e.g. after sign-in/sign-out) use to force it to re-fetch. It also shares the signed-in state via `getIsSignIn()` + `SIGN_IN_EVENT`; `Nav` uses it to show, as a button right of the language switch (`buttonNavClassName`/`buttonNavPrimaryClassName`), "Sign Out" when signed in and "Sign In" when not (Sign Up is linked from the Sign In page, not the navbar).

### App.Web styles and grid toolbar (Bar)
Shared Tailwind class strings live as constants in `App.Web/src/style.ts` (e.g. `buttonPrimaryClassName`, `buttonGridClassName`, `textInputClassName`); reuse them instead of repeating class lists inline.

A `GridDto` has no `rows` of its own: its rows are split over `GridDto.tables` (`GridTableDto[]`, built with `gridTables(toolbarRows, dataRows, barRows)` in `util-grid.ts`), and `Grid.tsx` renders one html `<table>` per entry: `tables[0]` toolbar rows, `tables[1]` data rows (header, find and data rows, or a dialog's content; `GridCommandEnum.New` rows are appended here), `tables[2]` the `gridBarRow()`.

`GridCustomEnum.Bar` (rendered in `gridCustomContent` in `Grid.tsx`) follows the typical data grid toolbar layout: a `gridBarClassName` strip (light gray, bordered, rounded top, `justify-between`, wraps on narrow screens) with two groups:
- **Left — actions:** `New` (the main action, `buttonBarPrimaryClassName`, solid blue; hidden if `GridSettingDto.isNewHide`, e.g. for generated rows), then `Save` and `Reload` (secondary, `buttonBarClassName`, white outlined), then Previous/Next row as icon-only buttons (`buttonBarIconClassName`, up/down chevrons): they move `selectedRowIndex` to the previous/next data row of the current page like a click on it (keeping the selected column, so `isSelectPatch` grids still send `GridCommandEnum.Select`); Next without a selected row selects the first row; disabled on the first/last row.
- **Right — paging:** "Rows per page:" select, "Page X of Y", then Previous/Next as icon-only buttons (`buttonBarIconClassName`, inline SVG chevrons with `aria-label`/`title`), disabled on the first/last page.

New toolbar buttons use these `buttonBar*` classes (not `buttonPrimaryClassName`): only the main action is primary, everything else secondary.
